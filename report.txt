## 4. Дефекты
ID: BUG-01
Требование: R03
Название: Не удерживается аварийное состояние при свежих данных.
Исходное состояние: pump=false, vent=false, fault=false
Шаги: 1. Вход age=31 (авария). 2. Вход age=0, reset=false.
Ожидаемый результат: fault=true, насос выключен.
Основание: R03 (авария сохраняется, пока нет reset).
Фактический результат: fault=false, насос включился (расход 2).
Серьёзность: Высокая (безопасность).
Доказательство: tests-before.json / protocol-before.txt, сценарий S13.
Причина в candidate.js: В функции hold стояло условие input.age > 30, которое не давало удерживать аварию на свежих данных.
Исправление до/после: hold: (previous, input) => previous.fault && !input.reset && input.age > 30  ->  hold: (previous, input) => previous.fault && !input.reset.
Регрессия: S13, S14 (PASS).

ID: BUG-02
Требование: R09
Название: Неверный приоритет распределения бюджета (насос важнее вентиляции).
Исходное состояние: pump=false, vent=false, fault=false
Шаги: 1. Вход temp=32, humidity=20, budget=3.
Ожидаемый результат: vent=true, pump=false, used=3.
Основание: R09 (вентиляция стоит 3, рассматривается первой).
Фактический результат: pump=true, vent=false, used=2.
Серьёзность: Высокая (перегрев).
Доказательство: tests-before.json / protocol-before.txt, сценарий S16.
Причина в candidate.js: В функции order стоял порядок ['pump', 'vent'].
Исправление до/после: order: () => ['pump', 'vent'] -> order: () => ['vent', 'pump'].
Регрессия: S15, S16 (PASS).

ID: BUG-03
Требование: R05
Название: Ошибка на границе гистерезиса (включение насоса при humidity=35).
Исходное состояние: pump=false, vent=false, fault=false
Шаги: 1. Вход humidity=35, temp=20.
Ожидаемый результат: pump=false (сохранение предыдущего).
Основание: R05 (при 35<=humidity<45 состояние сохраняется).
Фактический результат: pump=true.
Серьёзность: Средняя (избыточный полив).
Доказательство: tests-before.json / protocol-before.txt, сценарий S17.
Причина в candidate.js: В функции pumpStart стояло нестрогое неравенство humidity <= 35.
Исправление до/после: pumpStart: humidity => humidity <= 35 -> pumpStart: humidity => humidity < 35.
Регрессия: S17, S21 (PASS).

Минимизация (Этап 5):

## 6. Изменение 2.1 и свойства
Изменение R05: полив при humidity<40. Затронуты тесты на границе 35-40. 
Минимальные сценарии 2.1: 1) humidity=39.9 (ожидаем ВКЛ). 2) humidity=40 (ожидаем сохранение). 3) humidity=45 (ожидаем ВЫКЛ). 
Почему FAIL относительно 2.0 ожидаем: В версии 2.0 тест на 39.9 ожидает ВЫКЛ, поэтому на стенде 2.0 он упадет. Это различие спецификаций, а не дефект.
Свойства:
1. used <= budget (при валидном входе).
2. Если fault=true и reset=false, то pump=false, vent=false.
3. При отсутствии запретов и достаточном бюджете, в зоне 35<=h<45 насос сохраняет состояние.
Бюджет 2->3 при двух запросах: Насос может выключиться, так как вентиляция (стоимость 3) имеет приоритет и забирает весь бюджет. Это не дефект (R09).

## 7. Взаимная проверка
Рецензент: Самоаудит по протоколам
Проверенный оракул: Пересчитан вручную тест S16 (бюджет=3, ожидание vent=true). Проверено, что вентиляция стоит 3 и рассматривается первой.
Предложенная непроверенная комбинация: Проверка сброса аварии без предварительной аварии (reset=true на нормальных данных) — гистерезис не сбрасывается.
Результат воспроизведения: Совпал с ожиданиями.

## 8. Решение
Принять учебную сборку (после исправления 3 дефектов).
Доказательства: 100% покрытие учебных исходов (24/24), 100% убитых мутаций (8/8), протоколы до/после, карточки дефектов, ручные расчеты.
Остаточные риски: Отсутствие реального оборудования и физики. Модель не проверяет износ датчиков. Не все комбинации из 8 возможных блокировок проверены отдельно (только минимальные опыты для независимости).
Что потребовалось бы для реальной системы: Журналирование времени, подтверждение команд, физические датчики состояния механизмов.
